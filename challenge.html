Before you wire this into SVGator, one correction. SVGator's MCP server is real, but it is not at svgator.com — that is the marketing site. The endpoint is https://mcp.svgator.com/mcp, it speaks Streamable HTTP, and it authenticates with OAuth 2.1 against your own SVGator account.

That server is not reachable from this conversation: Arena has no SVGator connector, and the endpoint gates every request behind a bearer token from your sign-in. So these templates were authored and verified locally. The paths below are how you land them in SVGator from your own client, in about two minutes.

Getting this into SVGator

Path A · no account needed

Drop a template straight into the web

These files are finished animated SVGs. They need no build step and no tooling — paste and ship.

<img src="templates/02-orbit-loader.svg" width="120" alt="Loading">

For retinting and control, inline it instead — the ring and wordmark use currentColor, so one CSS rule recolours them.

[data-tpl] svg { color: #FF3D7F; }
Path B · recommended

Connect the MCP server, then create the project

You own the project, the editor link, and the exports. Run this in Claude Code or any MCP-speaking client:

claude mcp add --transport http svgator \
  https://mcp.svgator.com/mcp

Then authenticate with /mcp → svgator. In claude.ai, add it as a custom connector with the same URL. Once connected:

  1. Call describe_shape for root, circle, path, keyframe, easing, paint.
  2. Patch any field name the reference disagrees with — that call needs no auth, so you can diff it before spending a create.
  3. create_project with templates/svgator-project.01-bloom.json.
  4. export_project → svg, inline: true to get the markup back.
Path C · fastest

Import into the visual editor

Open the SVGator editor, start a new project at 480×280 (or 120×120 for the loader and bell), and import the file. The elements arrive named — Petal 1…6, Outer Ring, Wordmark — which is the point of the naming discipline.

You then rebuild the keyframes by hand off the spec table under each preview. Slower, but you keep everything inside the GUI.

The kit, live

Speed scales dur; Delay/Stagger scales begin — together they retime the piece without touching a single keyframe value. Easing override rewrites keySplines uniformly, which is deliberately blunt: it shows you how much of the feel lives in the curve.

What was actually verified

Every frame was inspected, not assumed

The kit ships a filmstrip harness that drives the real timeline (pauseAnimations() + setCurrentTime(t)) and renders each template at six or seven points so the motion can be reviewed frame by frame instead of guessed from the markup.

That is how three bugs got caught: the bloom petals rendered fully visible at t=0 because a begin-delayed opacity animation leaves the element at its static value first; the loader's leading arc was 25% too long; and the badge ping faded before it read.

The linter knows the failure modes

tools/validate.py runs 42 checks: values ↔ keyTimes ↔ keySplines counts, monotonic keyTimes, parseable begin/dur, url(#…) resolution, dash lengths against real getTotalLength(), and the static-baseline lint that catches the flash-before-first-keyframe class of bug.

It also caught two defects in this very kit — a dashed stroke longer than its path, and an over-strict rule of its own (SMIL keyTimes may legally end below 1; the final value simply holds).
